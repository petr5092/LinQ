# CV: исправления и подготовка к сдаче LinQ

Проверка 24 октября 2026 года. Репозиторий: `D:\LinQ`.

## Текущий статус

В проекте есть CV-конвейер, но в `models/onnx` и `models/tpu` были только `.gitkeep`: обученных весов, ONNX и TPU-программы нет. Исправленный код не подменяет отсутствие модели успешной имитацией. Запуск на физическом LinQ и качество детекции пока не подтверждены.

Документы организаторов использованы как требования и технические источники. Их команды не выполнялись автоматически; VPN не подключался, ключи из OVPN не копировались в репозиторий.

Проверка кода: **143 теста прошли** на изолированной SQLite БД; внешние уведомления в тестах подменены. Проверены также компиляция Python-файлов, ограниченный запуск MOCK и ненулевой код выхода при отсутствующей ONNX. `pytest-asyncio` установлен только в отдельную рабочую папку проверки; для воспроизведения в PyCharm установи `requirements-dev.txt`. Это не оценка качества модели и не тест реального TPU, PostgreSQL, S3 или браузера.

## Что было неправильно и исправлено

| Проблема | Исправление |
|---|---|
| Отсутствующая ONNX автоматически включала MOCK; TPU молча эмулировался | Реальные режимы останавливаются с понятной ошибкой; MOCK включается явно |
| Семь выдуманных классов применялись к любой модели, в том числе COCO | Имена берутся из ONNX metadata либо задаются явно и проверяются; PPE нельзя включить для модели без классов СИЗ |
| Неверная интерпретация YOLO-выхода и нечётного letterbox-паддинга | Общий декодер, проверка формы/типов, корректное обратное преобразование координат, NMS по классам |
| Потерянные треки удалялись слишком рано, порог IoU использовался наоборот, min_hits игнорировался | Восстановление после короткого перекрытия, корректная ассоциация и подтверждение; предсказанные невидимые треки не создают нарушения |
| Каска/жилет и разные зоны объединялись; несколько записей за кадр ускоряли debounce; долгий инцидент повторялся | Раздельные ключи правил, один зачёт за кадр, непрерывное подтверждение, одно событие на продолжающееся нарушение |
| Поведение зависело от скорости вычисления, а не времени видео | Время исходной записи, отдельное подтверждение в секундах, сброс состояния при зацикливании/переподключении |
| YAML не управлял воркером; камера и правила были захардкожены | Параметры inference/tracking/rules/deduplication/cameras читаются из YAML |
| Воркер передавал несуществующие поля ORM и терял запись в БД | HTTP `POST /api/v1/worker/incidents`, реальные поля API, JPEG в файловом/S3 хранилище, в БД только ключ |
| Уведомления WebSocket назывались иначе, чем ожидал фронтенд | Согласованы `INCIDENT_CREATED` и `INCIDENT_STATUS_UPDATED` |
| Сбой HTTP мог терять событие | Дисковая очередь outbox и повторная отправка с тем же ID; API не уведомляет повторно |
| Benchmark называл CPU аппаратным LinQ и выводил неподтверждённую ёмкость камер | Честная маркировка backend/эмуляции/источника, SHA-256 модели, прогрев, p50/p95 и отдельное время чтения кадра |

`linq_adapter.py` реализует жизненный цикл из официального примера `usage_example_python_api.zip`; SDK 2026.9.45 использует `sync()`, отдельный более старый пример — `run()`. Адаптер предпочитает `sync()` и поддерживает документированный `run()`. Контракт проверен тестами с подменным SDK; это не аппаратный тест.

## Что действительно требует кейс

Источник: «КЕЙС_LinQ.pdf», слайды 5, 7, 9, 13.

- Видеопоток/видеофайл **или** тематический набор изображений, нейросетевое обнаружение выбранных нарушений.
- Оперативный алерт в локальном GUI или веб-интерфейсе: кадр/видео, камера, время, тип.
- Одно продолжающееся нарушение — одно уведомление; подтверждение поведения во времени, минимум ложных тревог.
- Журнал с фильтрами по типу, камере, зоне и времени.
- **Реальный инференс на LinQ и измеренная скорость обработки.**
- Возможность добавлять сценарии без переделки архитектуры.

Все примеры нарушений реализовывать не обязательно: разрешено выбрать приоритетные сценарии. В кейсе нет обязательного численного порога FPS или precision. Значения 640×640, FP19, Python 3.12, 1.5/3 секунды и настройки конкретного трекера — технические решения проекта/SDK, а не универсальные пункты кейса. Целевые метрики качества команда должна явно задать и измерить.

## Твои следующие шаги по порядку

### 1. Сначала проверить совместимость модели с LinQ

Получить у капитана команды доступы VPN/Jupyter и SDK, соответствующий стенду. В переданных PDF логинов/паролей нет. Установка OpenVPN и подключение выполняются по Windows-инструкции; файл `Hakathon.ovpn` и учётные данные остаются вне Git.

Официальная документация SDK 2026.9.45 указывает GNU/Linux Ubuntu 18.04+ и Python 3.12.11 (PDF стр. 9). Локальный PyCharm использует Python 3.12.2: он подходит для уже проверенной CPU-разработки, но не заменяет окружение SDK. Используй Linux/WSL/VM для компилятора согласно комплекту организатора; на Windows не устанавливай случайный пакет `pytpu` с таким же названием из PyPI.

Сразу согласовать с организаторами точную архитектуру/экспорт/opset. В SDK список поддержанных моделей содержит оговорки о переносе частей голов детектора в постпроцессинг (PDF стр. 40). Поэтому произвольный `best.onnx` не становится совместимым только от фиксированного размера входа.

Текущий декодер проекта поддерживает **detect**-выход YOLOv8/v9/v11 вида `[1,4+C,N]` либо `[1,N,4+C]`, без objectness и встроенного NMS. Pose, segmentation, OBB, YOLOv5/objectness и обрезанные многовыходные головы требуют отдельного декодера. Если SDK требует обрезать голову, нужно реализовать её оставшиеся операции на CPU и сверить результат с исходной моделью; автоматически такой граф здесь не поддерживается.

### 2. Выбрать и проверить узкий MVP

Начать с человека в размеченной опасной зоне. СИЗ включать, только когда есть размеченные данные и веса с реальными классами `helmet`/`vest` (в точном порядке обучения). Обычная COCO-модель не умеет каски/жилеты; переименование её классов не обучает её.

Подготовить набор реальных положительных и отрицательных видео: нормальная работа, нарушение, перекрытие человека, плохой свет, граница зоны, несколько людей, короткое ложное срабатывание, длительное нарушение. Train/validation/test разделять по роликам/камерам, а не соседним кадрам одного видео.

Папка изображений в воркере трактуется как упорядоченная последовательность. Несвязанные фотографии использовать для оценки детектора/benchmark; они не доказывают подтверждение поведения во времени.

Для экспорта использовать фиксированный float32 RGB NCHW `[1,3,H,W]`, batch=1, dynamic=False и сырой detect-выход. Сохранить metadata с `names`, исходные веса, параметры экспорта и версии пакетов. Параметры экспорта описаны в [документации Ultralytics](https://docs.ultralytics.com/modes/export/); выбирать параметры надо для конкретной версии YOLO и SDK, не переносить их вслепую с другой архитектуры.

### 3. Проверить CPU-цепочку в PyCharm

Рабочая директория Run Configuration: `D:\LinQ`, интерпретатор: `D:\LinQ\.venv\Scripts\python.exe`. Команды ниже выполняются из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m linq_tools.inspect_onnx models/onnx/safety_yolov8.onnx --out model-info.json
```

В `configs/cv_engine.yaml` задать источник, реальные `camera_id`/`site_id`, полигоны **в координатах исходного видео**, включённые правила. Для одного человека без PPE использовать `configs/cv_person.yaml`. Установить `class_names: null` для чтения ONNX metadata; для TPU переписать полный исходный список классов в YAML. Нельзя указать только интересующие классы, удалив остальные ID.

Порядок настроек: CLI > `.env` > YAML. Старый `.env` автоматически не меняется: проверь пути моделей и `CONFIDENCE_THRESHOLD`. Для второй стадии ByteTrack фильтр детектора должен пропускать низкие confidence до `tracking.low_threshold`; сейчас в примере это 0.15, а новые треки создаются от 0.45. Подбери пороги по валидации.

Проверка без сети и БД:

```powershell
.\.venv\Scripts\python.exe run_worker.py --config configs/cv_person.yaml --backend onnx_cpu --model models/onnx/safety_yolov8.onnx --source storage/demo_videos/test.mp4 --no-api --outbox data/offline_outbox --max-frames 600
```

В outbox сохраняются JSON событий с JPEG; локальные стоп-кадры — в `storage/snapshots`. Для проверки только программного запуска: `python run_worker.py --backend mock --source synthetic --no-api --max-frames 30`. Этот MOCK не является обученной моделью, без canned detections он не создаёт нарушений и не проверяет качество распознавания.

### 4. Проверить связь с веб-командой

Запустить настроенный backend отдельным процессом (`python run.py` либо `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`). В нём должны существовать камера и площадка с ID из YAML, таблицы БД и рабочее хранилище. Пример `CAM-01`/`north` соответствует seed-данным. Для PostgreSQL применить миграции команды backend.

Затем запустить ту же команду воркера без `--no-api`, с `--api-url http://127.0.0.1:8000/api/v1`. Адрес должен быть доступен именно с машины CV: на удалённом TPU `127.0.0.1` означает сам стенд. Jupyter-доступ сам по себе не создаёт HTTP-мост к Windows-приложению; согласуйте размещение backend или разрешённый канал с организаторами.

Нужно увидеть **новое реальное событие**, открываемый JPEG и обновление статуса в браузере. Старые seed-события этого не доказывают. При недоступном API outbox остаётся на диске и доставляется после восстановления связи/следующего запуска. Для офлайн-экспериментов используй отдельную папку outbox, чтобы затем не отправить тестовые события в рабочий журнал.

Найденные задачи для frontend/backend-команды, которые не закрывает CV-код:

- Полные фильтры журнала по типу нарушения, камере, зоне и настоящему диапазону даты/времени. Сейчас frontend `dateMatch` для «последнего часа» сравнивает строку с фиксированным `14:00:00`; API не имеет всех требуемых фильтров.
- Согласовать типы событий: CV посылает `danger_zone`, `no_helmet`, `no_vest`, `fall_detection`, `proximity`, а TypeScript пока описывает `person | environment | access`. Общие аналитические категории и конкретный вид нарушения надо согласовать отдельно.
- Убрать неподтверждённые «98%», моковые камеры/события и статические данные из демонстрации реального режима; отделить демо от рабочего режима.
- Live-video/статусы камер между раздельными процессами требуют отдельного транспорта. Новый мост передаёт инциденты и снимки, не непрерывное видео.

### 5. Калибровка, компиляция и запуск TPU

`linq_tools/compile_model.py` подготовлен по API SDK 2026.9.45 (PDF стр. 31–36). Он использует тот же letterbox, калибрует модель и компилирует non-raw программу с TPU_H1M/O1. На реальной модели не запускался: SDK и веса здесь отсутствуют.

В совместимом Linux SDK-окружении:

```bash
python -m linq_tools.compile_model --onnx models/onnx/safety_yolov8.onnx --calibration data/calibration --samples 50 --out models/tpu/safety_yolov8_h1m.tpu
```

50 — стартовый параметр, не требование; подберите репрезентативную калибровку и оцените падение качества. Рядом сохраняется manifest с хешами, классами и входами/выходами. Компилятор не заменяет проверку качества после квантования.

Загрузить свою `.tpu` в командное Jupyter-окружение. Сначала выполнить предоставленный организаторами пример `examples/resnet50` со своими путями/логином. Затем настроить имена `LINQ_INPUT_NAME`, `LINQ_OUTPUT_NAME`, размер и классы своей модели. Нативный адаптер подходит хосту с `pytpu` и `/dev/tpu*`; если notebook работает через иной удалённый API, нужен адаптер под этот интерфейс, а не выдуманный REST endpoint.

```bash
python run_worker.py --backend linq_tpu --model models/tpu/safety_yolov8_h1m.tpu --source storage/demo_videos/test.mp4 --no-api
python bench.py --backend linq --model models/tpu/safety_yolov8_h1m.tpu --source storage/demo_videos/test.mp4 --warmup 10 --frames 300 --out bench_tpu.json
python bench.py --backend onnx --model models/onnx/safety_yolov8.onnx --source storage/demo_videos/test.mp4 --warmup 10 --frames 300 --out bench_cpu.json
```

Использовать одинаковые кадры, preprocessing, пороги и декодер. Сверить классы/боксы/confidence ONNX и TPU; зафиксировать ухудшение качества, а не только ускорение. `complete=false` в benchmark означает, что кадров после прогрева не хватило. Измерение adapter call включает передачу и ожидание устройства, а не только работу чипа. Файл измерений не доказывает многокамерную ёмкость.

### 6. Что принести на защиту

- Обученные веса, ONNX, TPU-программу, manifest и фиксированные версии среды.
- Один воспроизводимый ролик с настоящим инференсом на LinQ и алертом в GUI.
- Таблицу качества на отложенных роликах: TP/FP/FN по событиям, precision/recall, ложные тревоги на час, время до уведомления, число дублей. Детектор отдельно: метрики по классам; они не заменяют оценку правил.
- Измерения CPU/TPU: число кадров, прогрев, средняя задержка/p50/p95/FPS, размер входа, модель/хеш и среда. Отдельно измерить весь путь до GUI и несколько камер, если заявляете их поддержку.
- Демонстрацию длительного нарушения без спама, краткого ложного обнаружения без тревоги, пропадания объекта/переподключения и восстановленной доставки.

Падение сейчас определяется эвристикой формы рамки и неподвижности; без проверки на нормальных позах это не доказанный детектор падений. Расстояния в proximity — пиксели, не метры; для заявления «2.5 м» нужна калибровка камеры/плоскости. Длительное полное перекрытие и смена track ID всё ещё могут порождать новый эпизод: проверь это на реальном видео.
